# Plan: NCLCON-13451 — Content Security Policy Hardening

## Requirement
Apply a hardened multi-directive CSP header to both portals via Azure Front Door.
Both pipelines write to the SAME Front Door ruleset — whichever deploys last overwrites the
other — so the CSP value must be the union of all external dependencies from both portals,
set identically in both repositories.

## Common CSP Value (identical in both repos)
```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com https://cdnjs.cloudflare.com https://cdn.linearicons.com https://cdn.jsdelivr.net; font-src 'self' data: https://fonts.gstatic.com https://cdnjs.cloudflare.com https://cdn.linearicons.com https://cdn.jsdelivr.net; frame-src 'self' https://app.powerbi.com; frame-ancestors 'none'; connect-src 'self' https://*.b2clogin.com https://*.msauth.net https://login.microsoftonline.com; object-src 'none'; base-uri 'self'
```

## Approach Chosen
**Approach 1:** Single PR per repo. SelfService extracts 2 inline scripts from index.html as
a pre-condition within the same PR, then both repos apply the common CSP. ~45 min total.

## Alternatives Considered
- **Approach 2** (two-phase SelfService PRs) — over-engineered for this risk level; extra PR lifecycle overhead
- **Approach 3** (ship unsafe-inline now) — deliberately ships incomplete security control; anti-pattern

## Key Decisions
- CSP must be the UNION of both apps' requirements because both pipelines overwrite the same Front Door ruleset
- SelfService inline scripts (OIDC callback + feedback button) MUST be extracted before script-src 'self' applies
- `'unsafe-inline'` retained in style-src only (styled-components + Angular runtime styles) — not in script-src
- `frame-ancestors 'none'` rather than 'self' — stronger clickjacking protection (no same-origin framing needed)
- `*.b2clogin.com` wildcard covers all B2C tenants (QA: connectv2qa.b2clogin.com, prod: different subdomain)

## Architecture Impact
- No new service boundaries or dependencies introduced
- Azure Front Door ResponseRuleSet gains a hardened policy — both portals benefit from the same deploy
- ARCHITECTURE.md for both product repos should note the shared Front Door ruleset constraint

## Testing Strategy
- **Unit:** csp-headers.test.ts / csp-headers.spec.ts read parameters.frontdoor.json directly and assert all directives
- **Integration (manual):** B2C login flow, Power BI reports page, CDN fonts/icons rendering must be verified in QA after deployment
- **Regression risk:** Prior NCLCON-13049 test pattern is safe; the added connect-src/frame-src/style-src entries cover the 3 known failure modes from the revert

## Rollback Plan
- **How to undo:** Revert the parameters.frontdoor.json change in either/both repos and redeploy
- **Data safety:** No data mutations — config-only change
- **Blast radius if it fails in prod:** B2C login or Power BI could break for all users of the affected portal — monitor login and reports immediately after deploy
- **Point of no return:** None — fully reversible at any time

## Risk Assessment
| Risk | Probability | Impact | Mitigation |
|---|---|---|---|
| B2C auth XHR blocked | Low (connect-src covers *.b2clogin.com) | High | Verify login flow in QA before promoting |
| Power BI iframe blocked | Low (frame-src covers app.powerbi.com) | Medium | Verify Reports page in QA |
| CDN fonts/icons break (SelfService) | Low (style-src/font-src cover all 4 CDNs) | Low | Visual check in QA |
| Angular/styled-components styling breaks | Low (style-src 'unsafe-inline' retained) | Medium | Verify page renders correctly |
| Missed external resource | Low-Medium | Medium | Monitor browser console for CSP violations after deploy |
