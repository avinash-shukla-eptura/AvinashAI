## Root Cause (code-grounded)

The exception originates from the Azure.Data.Tables SDK's reflection-based entity serializer.
`MeetingUpsertEntity` (implements `ITableEntity`) declares three date/time properties
as the CLR `DateTime` / `DateTime?` type:

```
// Connect-Telemetry/Condeco.Connect.Telemetry.ProcessUpsertLogging/Models/MeetingUpsertEntity.cs
public DateTime? DateTimeFrom { get; set; }   // line 18
public DateTime? DateTimeTo   { get; set; }   // line 20
public DateTime  EnqueuedTimeUtc { get; set; } // line 28
```

Azure Table Storage persists all date/time values as `DateTimeOffset` (ISO 8601 with timezone).
When `TableClient.UpsertEntityAsync` serializes the entity for the wire format it calls
`DateTimeOffset op_Implicit(DateTime)`, which succeeds for `DateTimeKind.Utc` values.
The cast exception occurs when the SDK round-trips — on certain SDK paths (e.g., conflict
resolution, optimistic-concurrency retry, or table-scan during `CreateIfNotExists`) it
attempts to copy a `DateTimeOffset` value back into the `DateTime` property via reflection,
which throws `InvalidCastException` because there is no implicit conversion in that direction.

**Fix:** Change all three properties in `MeetingUpsertEntity` from `DateTime` / `DateTime?`
to `DateTimeOffset` / `DateTimeOffset?` and update the constructor to convert explicitly,
safe because `MeetingUpsert`'s setters normalize all values to UTC via `.ToUniversalTime()`.

No changes are required in `MeetingUpsert.cs` (source model) or `ProcessUpsertLogging.cs`
(the function trigger).

## Eight-Section Triage Description

### 1. Summary

**[Bug]** `ProcessUpsertLogging` Azure Function throws `System.InvalidCastException:
Unable to cast object of type 'System.DateTime' to type 'System.DateTimeOffset'` when
writing to Azure Table Storage via `TableClient.UpsertEntityAsync`. Four exceptions were
observed in Application Insights on 14 Sep 2026 against
`devicehub-upsertlogging-westeurope-qa`. The cause is `MeetingUpsertEntity` declaring
date/time fields as `DateTime` / `DateTime?` instead of `DateTimeOffset` / `DateTimeOffset?`,
which is the type the Azure.Data.Tables SDK requires on `ITableEntity` implementations.

---

### 2. Acceptance Criteria

1. **AC-1 — No cast exception:** After the fix is deployed to QA, Application Insights
   shows zero `InvalidCastException` exceptions originating from
   `Condeco.Connect.Telemetry.ProcessUpsertLogging` for a continuous 24-hour window with
   normal traffic.
2. **AC-2 — Data integrity:** Records written to the `meetingUpsertLog` Azure Storage table
   contain correct UTC date/time values in `DateTimeFrom`, `DateTimeTo`, and
   `EnqueuedTimeUtc` columns (verifiable by querying the table directly).
3. **AC-3 — Backward compatibility:** Existing rows in the table are not corrupted; new rows
   can be queried and deserialized without error.
4. **AC-4 — No regression in sibling services:** Other functions in the
   `Condeco.Connect.Telemetry.*` namespace remain green in QA.

---

### 3. Technical / Functional Requirements

- **TR-1:** In
  `Connect-Telemetry/Condeco.Connect.Telemetry.ProcessUpsertLogging/Models/MeetingUpsertEntity.cs`,
  change:
  - `public DateTime? DateTimeFrom` → `public DateTimeOffset? DateTimeFrom`
  - `public DateTime? DateTimeTo`   → `public DateTimeOffset? DateTimeTo`
  - `public DateTime  EnqueuedTimeUtc` → `public DateTimeOffset EnqueuedTimeUtc`
- **TR-2:** Update `MeetingUpsertEntity` constructor to convert from the source `DateTime`
  values using explicit `DateTimeOffset` construction with `TimeSpan.Zero` offset (safe
  because `MeetingUpsert` setters always call `.ToUniversalTime()`):
  ```csharp
  DateTimeFrom = meetingUpsert.DateTimeFrom.HasValue
      ? new DateTimeOffset(meetingUpsert.DateTimeFrom.Value, TimeSpan.Zero)
      : null;
  DateTimeTo = meetingUpsert.DateTimeTo.HasValue
      ? new DateTimeOffset(meetingUpsert.DateTimeTo.Value, TimeSpan.Zero)
      : null;
  EnqueuedTimeUtc = new DateTimeOffset(meetingUpsert.EnqueuedTimeUtc, TimeSpan.Zero);
  ```
- **TR-3:** Audit any other `ITableEntity` implementations in the `Connect-Telemetry`
  solution that may have the same pattern; fix them in the same PR.
- **TR-4:** No changes to `MeetingUpsert.cs` or `ProcessUpsertLogging.cs` unless TR-3
  surfaces a related issue in those files.

---

### 4. API / Interface Contracts

- The Azure Table Storage schema for `meetingUpsertLog` is not formally versioned. Changing
  `DateTime` → `DateTimeOffset` on the entity does not alter the wire format — Azure Table
  Storage stores all dates as ISO 8601 UTC strings regardless of the CLR type.
- `ITableEntity.Timestamp` (the SDK-managed column) is already `DateTimeOffset?` and is not
  affected.
- The Event Hub trigger signature (`EventData[]`) is unchanged.
- No API surface exposed to external consumers; this is an internal processing function.
