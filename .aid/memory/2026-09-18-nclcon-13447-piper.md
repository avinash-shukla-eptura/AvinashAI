## Section 1 — Problem Statement

**What is broken and where.**  
The `devicehub-upsertlogging` Azure Function (project `Condeco.Connect.Telemetry.ProcessUpsertLogging`, repo `Connect-Telemetry`) throws an unhandled `InvalidCastException` — "Unable to cast object of type 'System.DateTime' to type 'System.DateTimeOffset'" — when it attempts to write a `MeetingUpsertEntity` row to Azure Table Storage via the `Azure.Data.Tables` SDK (v12.9.1). The exception surfaces in Application Insights resource `devicehub-upsertlogging-westeurope-qa`.

**Observable symptom (source: NCLCON-13447 description, Adhikansh Garg, 2026-09-16):**
- 4 exceptions logged on 2026-09-14 at 17:08 UTC and 17:45 UTC, each count appearing twice in Application Insights.
- Time range monitored: 2026-09-13 to 2026-09-16.
- Environment: QA only; production impact unknown at time of filing.

**Business impact:** Every affected Event Hub message that triggers the cast failure is not committed to Azure Table Storage. The Event Hub checkpoint is not advanced (because the Azure Function re-throws on line 64 of `ProcessUpsertLogging.cs`), so the runtime may retry the message, causing duplicate exception appearances in Application Insights. Logging continuity is broken for the affected booking events.

## Section 2 — Root Cause Hypothesis

**Source: code inspection of `Connect-Telemetry` repo, 2026-09-18.**

`MeetingUpsertEntity` (file: `Condeco.Connect.Telemetry.ProcessUpsertLogging/Models/MeetingUpsertEntity.cs`) implements `Azure.Data.Tables.ITableEntity`. Three of its properties are declared as `DateTime`/`DateTime?`:

| Property | Type | Always populated? |
|---|---|---|
| `DateTimeFrom` | `DateTime?` | No — null for delete-type events |
| `DateTimeTo` | `DateTime?` | No — null for delete-type events |
| `EnqueuedTimeUtc` | `DateTime` | Yes — always set (line 53, `ProcessUpsertLogging.cs`) |

The Azure.Data.Tables SDK v12 serializes `ITableEntity` properties by boxing their values as `object` and then pattern-matching or casting to the expected Table Storage OData type (`Edm.DateTime` maps internally to `DateTimeOffset`). When the SDK encounters a boxed `DateTime` value and tries to unbox it as `DateTimeOffset`, the CLR throws `InvalidCastException` — the two are unrelated value types; no unboxing coercion exists between them, even though an implicit C# conversion operator does.

**Why intermittent (4 occurrences in 3 days):**  
`DateTimeFrom` and `DateTimeTo` are nullable. When the incoming Event Hub message represents a "Deleted" meeting event, `MeetingState` is set to "Deleted" (line 55 of `ProcessUpsertLogging.cs`) and the JSON payload often omits `dateTimeFrom`/`dateTimeTo`, leaving them `null`. Null properties are skipped by the SDK serializer. Only messages where `dateTimeFrom` or `dateTimeTo` are present trigger the cast failure. `EnqueuedTimeUtc` is non-nullable `DateTime` and is always written; the SDK may handle non-nullable `DateTime` differently (e.g., as a direct `TableEntityProperty` path) — or the failure on nullable `DateTime?` precludes reaching it. The 4 exceptions correspond to 2 Event Hub messages that carried non-null date-time values (each appearing twice: first attempt + function host retry after the re-throw on line 64).

**Evidence gap:** No stack trace from Application Insights was available in Jira (screenshots were attached as images, not text). The exact call site within Azure.Data.Tables SDK could not be confirmed from source. The hypothesis is consistent with the SDK version (12.9.1), the entity model, and the .NET behaviour of boxing/unboxing.

## Section 3 — User Stories

**Story 1 (source: NCLCON-13447 expected result, Adhikansh Garg):**  
As the telemetry system, when an Event Hub message containing meeting upsert data (including non-null `dateTimeFrom` or `dateTimeTo` values) is received, the `ProcessUpsertLogging` function should successfully persist the event to Azure Table Storage without throwing a cast exception, so that no exceptions appear in Application Insights for this code path.

**Story 2 (inferred from code, line 60-64 of `ProcessUpsertLogging.cs`):**  
As an operator, when any exception does occur during message processing, the error should be logged once (not duplicated) and the function should advance the Event Hub checkpoint so that the same message is not retried indefinitely.

**Note on Story 2:** The current `throw;` on line 64 is the correct pattern for poison-message detection in Event Hub triggers (Azure Functions will retry then dead-letter). Story 2 is flagged as an open question — the retry behaviour is intentional but may need PM confirmation. Story 2 is NOT in scope for this fix unless PM explicitly includes it.

## Section 4 — Acceptance Criteria

All criteria are measurable. None use "fast", "seamless", "intuitive", "scalable", or "secure" without a threshold.

**AC-1 (core fix):**  
Given a `MeetingUpsertEntity` where `DateTimeFrom` and/or `DateTimeTo` are non-null, when `UpsertEntityAsync` is called, then no `InvalidCastException` with message "Unable to cast object of type 'System.DateTime' to type 'System.DateTimeOffset'" is thrown. Verified by: unit test constructing `MeetingUpsertEntity` with non-null date values and asserting no exception from the SDK serialization path; or by integration test writing to a real/emulated Table Storage endpoint.  
_Source: NCLCON-13447 expected result._

**AC-2 (null safety):**  
Given a `MeetingUpsertEntity` where `DateTimeFrom` and `DateTimeTo` are null, when `UpsertEntityAsync` is called, then the entity is written successfully and the null properties are omitted from the Table Storage row.  
_Source: inferred from nullable declarations in `MeetingUpsert.cs`._

**AC-3 (UTC preservation):**  
Given that `MeetingUpsert.DateTimeFrom` and `MeetingUpsert.DateTimeTo` call `ToUniversalTime()` on set, when the corresponding `DateTimeOffset` properties are written to Table Storage, then their UTC offset is zero (`+00:00`). Verified by reading the persisted row back and asserting `Offset == TimeSpan.Zero`.  
_Source: `MeetingUpsert.cs` setter logic, lines 52 and 65._

**AC-4 (EnqueuedTimeUtc preservation):**  
Given that `EnqueuedTimeUtc` is derived from `eventData.EnqueuedTime.UtcDateTime` (a `DateTime` with `Kind=Utc`), when converted and written as `DateTimeOffset`, the stored value equals `DateTimeOffset.FromFileTime` equivalent with offset `+00:00`. Verified by asserting the round-tripped value matches the original `eventData.EnqueuedTime` (allowing up to 1 ms rounding from `UtcDateTime` conversion).  
_Source: `ProcessUpsertLogging.cs` line 53._

**AC-5 (no regression in other telemetry services):**  
The `MeetingUpsert` model (in `ProcessUpsertLogging/Models/MeetingUpsert.cs`) must remain unchanged — it is serialized from JSON via Newtonsoft.Json and is not written directly to Table Storage. Only `MeetingUpsertEntity` (the ITableEntity implementation) must be changed.  
_Source: code inspection of `ProcessUpsertLoggingHelper.cs` — only `MeetingUpsertEntity` is passed to `UpsertEntityAsync`._

**AC-6 (no Application Insights exceptions for this error class in QA, 48 hours post-deploy):**  
After deploying the fix to `devicehub-upsertlogging-westeurope-qa`, the Application Insights exception count for messages matching "Unable to cast object of type 'System.DateTime' to type 'System.DateTimeOffset'" must be zero over a 48-hour observation window.  
_Source: NCLCON-13447 description, time range observed._

## Section 8 — Contradictions

**CONTRA-1:**  
`MeetingUpsert.DateTimeFrom` and `MeetingUpsert.DateTimeTo` are `DateTime?`, and their setters normalise to UTC via `ToUniversalTime()`. However, `MeetingUpsertEntity.DateTimeFrom` and `MeetingUpsertEntity.DateTimeTo` are also declared as `DateTime?` — they receive the UTC-normalised value from the DTO but then the SDK tries to cast this `DateTime` (Kind=Utc) to `DateTimeOffset`, which fails. There is a design inconsistency: the DTO uses `DateTime` throughout, while Azure Table Storage / the SDK expect `DateTimeOffset` on `ITableEntity` properties. This inconsistency was never caught at compile time because `ITableEntity` does not constrain property types.  
_This is a design defect, not a conflict in requirements. It is surfaced here for PM awareness._

**CONTRA-2:**  
The commented-out line in `MeetingUpsert.cs` (line 59: `//public DateTime? DateTimeTo { get; set; }`) suggests that the property was previously a simple auto-property and was later replaced with the backing-field setter. This change introduced the UTC normalisation, which is correct. However, it may have been done in isolation without updating `MeetingUpsertEntity` to `DateTimeOffset`. No contradictory requirements exist; this is an implementation gap.  
_Source: `MeetingUpsert.cs` line 59, code inspection 2026-09-18._

## Section 9 — Edge Cases

**EC-1:** Incoming JSON with no `dateTimeFrom`/`dateTimeTo` fields — `DateTime?` is null in DTO, `DateTimeOffset?` will be null in entity. SDK skips null properties. No exception. (This is the common case for delete events — explains intermittency.)

**EC-2:** Incoming JSON with `dateTimeFrom` as an ISO 8601 string with explicit timezone offset (e.g., `"2026-09-14T17:08:00+02:00"`). Newtonsoft.Json parses this as `DateTimeKind.Local`. The setter calls `ToUniversalTime()`, converting to UTC. The constructor must convert to `DateTimeOffset` with `TimeSpan.Zero` offset. `new DateTimeOffset(dt.Value)` where `Kind=Utc` is safe. `new DateTimeOffset(dt.Value)` where `Kind=Unspecified` throws — the UTC normalisation in the setter prevents this case.

**EC-3:** Incoming JSON with `dateTimeFrom` as a partial date string that Newtonsoft.Json cannot parse. `JsonConvert.DeserializeObject<MeetingUpsert>` would throw or return null (handled by the null check on line 48-51 of `ProcessUpsertLogging.cs`). This path is already safe.

**EC-4:** `accountId` is null in the incoming payload. `PartitionKey` becomes `""` (empty string). Azure Table Storage accepts empty partition keys. This is an existing behaviour, not introduced by this fix.

## Section 10 — Assumptions

**ASS-1:** The Azure.Data.Tables SDK v12.9.1 does not support `DateTime` typed properties on `ITableEntity` in the specific code path that `UpsertEntityAsync` uses for nullable `DateTime?` values. This is an assumption based on the error message and code inspection; it has not been verified against the SDK source.  
_Confidence: High. This is the documented correct pattern per Azure SDK guidance._

**ASS-2:** No other service in the solution reads `MeetingUpsertEntity` rows from Table Storage and deserialises them back into a `MeetingUpsertEntity` object. If such a service exists, changing properties to `DateTimeOffset` would affect deserialisation. Inspection of the solution shows only `ProcessUpsertLoggingHelper.cs` writes to this table; no read-back service was found.  
_Confidence: High. Needs confirming by the implementing engineer before shipping._

**ASS-3:** The `meetingUpsertLogTable` is a dedicated logging table and is not shared with other services. If any external consumer reads from it and expects `DateTime` Edm type, changing to `DateTimeOffset` may affect interoperability. Azure Table Storage stores both as `Edm.DateTime`; the SDK difference is in the CLR representation, not the wire format.  
_Confidence: Medium. Wire format unchanged; CLR change is localised._
